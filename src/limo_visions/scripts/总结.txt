简单的“二值化+找线”任务。然而在真实沙盘仿真与实车部署中，光照剧烈变化、
地砖接缝与路侧阴影、水泥墙壁与绿色草坪反光、弯道大曲率与直道小曲率的切换、

--------------------------------------------------------------------------------
【坑 1】NumPy 多项式拟合病态矩阵条件数发散与 RankWarning 终端 I/O 阻塞
--------------------------------------------------------------------------------
1. 遇到的现象与表象:
   系统运行起来后，终端以每秒几百行的速度疯狂刷屏警告：
   "RankWarning: Polyfit may be poorly conditioned"
   终端被海量红黄警告淹没，看不到任何正常输出；更可怕的是，节点处理帧率从
   250 FPS 断崖式下跌至 30 FPS 以下，小车底盘控制出现肉眼可见的卡顿迟滞。

2. 物理与数学机理:
   在阶段四执行 RANSAC 鲁棒抽样拟合二次多项式 y = a*x^2 + b*x + c 时，每次
   随机抽取 3 个样本点求解参数矩阵。
   构建范德蒙矩阵 (Vandermonde Matrix) A = [[x1^2, x1, 1], [x2^2, x2, 1], [x3^2, x3, 1]]。
   - 当随机抽取的 2 个或 3 个点来自同一个滑动窗口横排，或者纵向间距极其微小
     (如 Δx < 0.01m) 时，范德蒙矩阵的列向量出现近乎完全的线性相关；
   - 矩阵的条件数 (Condition Number) 爆炸性发散 (κ(A) -> ∞)；
   - 奇异值分解 (SVD) 检测到数值秩亏损 (Numerical Rank Deficiency)，NumPy
     因而向标准错误流 (sys.stderr) 抛出 RankWarning。

3. 为什么不能简单粗暴地全局忽略 (全局 warnings.filterwarnings)？
   - 之前代码在文件顶部写了:
     warnings.filterwarnings('ignore', category=np.RankWarning)
   - 缺点与后果:
     a) 全局污染: 改变了整个 Python 进程乃至依赖它的其他 ROS 包的全局警告环境；
     b) 治标不治本: 并没有解决“抽取到病态采样点”的数学本质。既然矩阵是病态的，
        这次求出的多项式系数就是发散失真的，白白浪费了一轮 RANSAC 抽样配额；
     c) 隐蔽缺陷: 可能会掩盖系统其他数学模块真实的除零或秩亏错误。

4. 如果放任不管、不采取方案的后果:
   - 控制频率 30Hz，每秒执行 30 * 35 = 1050 次多项式拟合；
   - 如果每秒抛出上千次异常告警，标准错误输出流 (stderr) 的写入会彻底阻塞
     Python 的主事件循环与 GIL 锁，导致控制延迟从毫秒级飙升到几百毫秒，
     小车在弯道直接冲出跑道。

5. 为什么这样改？(最终解决方案: 数学先验阻断 + 局部上下文受控)
   - 【代数源头根治 (方案 C)】:
     在 RANSAC 抽样循环中，抽取 3 个点后首先进行样本间距校验：
     sample_x = bx[sample_idx]
     sorted_x = np.sort(sample_x)
     if (sorted_x[-1] - sorted_x[0] < 0.20) or (np.min(np.diff(sorted_x)) < 0.05):
         continue
     * 规则 1: 样本整体纵向跨度必须 >= 0.20m (杜绝整体过窄)；
     * 规则 2: 任意两采样点之间的纵向间距严格 >= 0.05m (杜绝同行近距点)。
     * 效果: 从数学源头上直接杜绝病态采样进入 polyfit，节省了计算开销，
       使 RANSAC 的每一次有效拟合都是健康良态的，收敛速度翻倍。
   - 【局部安全拟合 (方案 A)】:
     定义静态方法 _safe_polyfit(x, y, deg)，使用局部上下文管理器：
     with warnings.catch_warnings():
         warnings.simplefilter('ignore', np.RankWarning)
         return np.polyfit(x, y, deg)
     仅在拟合局部吸收偶发告警，移除文件顶部的全局屏蔽，代码优雅纯净。


--------------------------------------------------------------------------------
【坑 2】非黄色环境物体 (水泥墙、绿色草坪、路缘石、白色箭头) 严重误检
--------------------------------------------------------------------------------
1. 遇到的现象与表象:
   在 RViz 中观察 /lane_detect_image，发现图像中出现了极其庞大的白色亮斑
   (实测单帧误检像素高达 23,878 个点)！
   左侧的灰色水泥墙、道路两旁的绿色草坪、路缘石反光、甚至地面上刷的白色直行
   与转弯箭头全部变成了白色高亮，被算法当成了车道线。滑动窗口直接被带偏爬
   到了左边的水泥墙和草坪上，车道线检测完全瘫痪。

2. 物理与机理深度解剖:
   经读取 Gazebo 材质纹理 (road_grass_crosswalks_4k.png) 并在不同光度下实测，
   发现了原有代码存在两大致命缺陷：
   - 缺陷 A: 白顶帽形态学增强 (White Top-Hat) 做了逻辑或 (bitwise_or)！
     原代码写了: mask_combined = cv2.bitwise_or(mask_b, mask_tophat)
     白顶帽是纯灰度域的高通滤波（用来提取比周围背景亮的局部线状结构）。
     它【完全没有任何色彩分辨能力】！无论是白色箭头、白色斑马线、水泥墙边界，
     只要比地面亮，白顶帽就全部提出来。接着一个 bitwise_or 把它并入车道线，
     相当于“只要是亮的非黄色物体全都要”，颜色过滤器彻底被击穿！
   - 缺陷 B: LAB 空间 B 通道自适应阈值过低 (将中性灰全算成黄色)！
     原代码写了: b_thresh = max(128, int(bg_b + 2))
     在 OpenCV LAB 空间中，B 范围是 0~255，其中 128 是绝对中性灰 (黑白灰)！
     当小车在暗光或阴影下，背景中值 bg_b = 128，算出来的阈值仅仅是 130！
     实测各物体参数：
     * 灰色水泥墙: B = 132 >= 130 (误判为黄！)
     * 绿色草地与树木: B = 132~144 >= 130 (误判为黄！)
     * 沥青地面微噪: B = 134 >= 130 (误判为黄！)
   - 缺陷 C: 缺失 HSV 饱和度与色相约束！
     水泥墙、沥青路、白色标线的饱和度极低 (S <= 25)，草坪虽然饱和度高但色调
     是绿色 (H ≈ 58)。原代码没有 HSV 约束，导致它们被全盘接纳。

3. 不采用正确方案的严重后果:
   - 滑窗直方图底部峰值 argmax 直接定位在墙壁 ($x \approx 100$)；
   - 算法认为“车道线在左侧水泥墙里”，输出的物理横向偏差严重失真；
   - 控制器执行剧烈打舵，小车直接以全速撞上水泥墙，无法完成任何一圈循迹。

4. 为什么这样改？(最终解决方案: HSV + LAB 双空间协同提纯)
   - 【彻底铲除白顶帽的 bitwise_or】:
     车道线检测的核心任务是【提取黄色】，绝不能用无色彩鉴别力的顶帽做逻辑或！
   - 【引入 HSV 物理空间强约束】:
     * 色调 H 严格限制在 [13, 35]: 100% 滤除绿色草坪 (H=40~85) 与天空蓝；
     * 饱和度 S 严格限制 >= 50: 100% 滤除水泥墙 (S=24)、沥青路 (S=19) 和
       白色斑马线/箭头 (S=18) 等无色彩物体；
     * 明度 V 限制 >= 30。
   - 【引入 LAB 空间双通道二次交叉确认】:
     * B 通道 >= 138 (确保具有显著黄色偏置，与中性灰 128 拉开绝对差距)；
     * A 通道 >= 118 (抑制草坪绿色分量，草坪通常 A <= 115)；
     * 执行逻辑交集: mask_yellow = cv2.bitwise_and(mask_hsv, mask_lab)。
   - 【形态学微小噪斑过滤】:
     采用 3x3 开运算 (MORPH_OPEN) 消除极微弱离散散斑，5x5 闭运算平滑连通。
   - 【实测改善效果】:
     非黄色误检像素从 23,878 点直接下降至 0 点 (100% 根除)！
     黄色车道线像素 4,825 点完整保留，滑窗基准中心精准锁定在车道线上。


--------------------------------------------------------------------------------
【坑 3】微光极夜 (10%) 至阳光满光 (100%) 光照剧变与非线性逆 Gamma 自适应
--------------------------------------------------------------------------------
1. 遇到的现象与表象:
   在自然日照 (100% 光照) 下调试良好的黄色检测阈值，一旦通过 Gazebo 插件将光照
   调为 20% (黄昏暗光) 或 10.5% (极夜微光)，整张图像漆黑一片，黄色车道线消失，
   节点发布 center_x = -1.0，提示完全丢线，小车触发紧急刹车停滞。

2. 物理机理剖析:
   单目 CMOS/CCD 相机在低照度环境下，光子到达传感器的通量极其微弱。
   若直接采用固定阈值提取：
   - 强光下黄色标线像素明度 V > 180，B > 180；
   - 10% 极暗微光下，黄色标线被压缩至 V ≈ 12，L ≈ 7；
   - 若简单粗暴调低全局阈值，那么在强光下就会引发严重的噪声过曝；若调高阈值，
     暗光下又寸步难行。
   - 【为什么不能用线性增益乘法 (img * factor)】:
     乘法会按比例放大暗部噪声，导致低量化阶梯被拉扯出严重的斑块噪点，且容易
     在局部高光处产生饱和截断 (Clipping)。

3. 不采用自适应机制的后果:
   - 自动驾驶系统只能在特定固定的人工光照下工作，一旦遇到隧道、树荫遮挡、
     晨昏交替或阴雨天气，视觉感知瞬间失效，无法达到毕业设计与工业级落地要求。

4. 为什么这样改？(最终解决方案: 7 级照度自适应 + 非线性逆 Gamma 查表)
   - 在阶段一采样小车近场路面 (Y: 280~480, X: 0~400) 的亮度均值 mean_l；
   - 划分为 7 级动态工况: 极夜深渊微光 (0.20)、深渊暗光 (0.25)、极暗微光 (0.35)、
     微光黄昏 (0.45)、局部浓荫 (0.60)、正常日照 (0.80)、高亮强光 (1.00)；
   - 预计算 7 张无符号整型逆 Gamma 查找表 (LUT):
     LUT[i] = ((i / 255.0) ** gamma) * 255
     在微秒级时间内完成对数动态范围提升，既大幅拉伸暗部弱黄色对比度，又保护
     亮部不饱和；
   - 利用色度（Hue）在光学成像中对光照强弱的天然不变量特性，在拉伸后的图像上
     执行 HSV 提取，实现在 10% 极夜至 100% 烈日下全天候高精识别。


--------------------------------------------------------------------------------
【坑 4】像素二维平面坐标系直接算偏差导致的几何非线性畸变与控制震颤
--------------------------------------------------------------------------------
1. 遇到的现象与表象:
   初学者常直接在图像上取车道线横坐标 u 与图像中轴线 320 的偏差 (e_px = u - 320)，
   将像素偏差直接当成误差送给控制器打舵。
   实车测试时发现：小车直道巡航疯狂“画龙”剧烈摆头，入弯时则转向不足冲出赛道；
   调整 PID 增益时，在直道调稳了，入弯就失灵；弯道调好了，直道又剧烈振颤。

2. 几何与数学本质:
   针孔相机成像是典型的非线性透视投影 (Perspective Projection)：
   - 在纵向深度近处 (如 v=450)，1 个像素对应的地面物理距离可能仅为 0.5 毫米；
   - 在纵向深度远处 (如 v=260)，1 个像素对应的地面物理距离可能高达 2~5 厘米；
   - 像素误差不仅是非线性的，且与车身姿态 (俯仰角 pitch、翻滚角 roll) 强耦合。
   - 像素空间没有“米 (m)”的物理量纲，下游控制器无法计算真正的侧向加速度与切线夹角。

3. 不采用逆透视映射 (IPM) 的后果:
   - 控制算法完全丧失物理意义，调参沦为不可解释的“玄学调参”；
   - 一旦车速发生改变，控制律彻底崩溃失效，无法满足阿克曼底盘动力学控制标准。

4. 为什么这样改？(最终解决方案: 严密推导物理针孔逆透视映射 IPM)
   - 基于安装物理参数: 离地高度 h_cam = 0.396m，下俯倾角 pitch = 0.2618 rad (15°)，
     光心距底盘回转中心前向偏置 x_cam_offset = 0.185m；
   - 严格推导逆透视射线与地平面的几何相交公式：
     xc = (u - cx) / fx,  yc = (v - cy) / fy
     r_down = sin(pitch) + cos(pitch) * yc
     dist_scale = h_cam / r_down
     x_body = dist_scale * (cos(pitch) - sin(pitch) * yc) + x_cam_offset
     y_body = -dist_scale * xc
   - 将所有图像像素全部投影到底盘刚体米制物理坐标系 (x_body, y_body)；
   - 输出以米为单位的真实物理偏差 e_y (m) 和弧度为单位的航向角 e_psi (rad)，
     使下游斯坦利控制器输入严密、控制丝滑稳定。


--------------------------------------------------------------------------------
【坑 5】多项式固定阶数在“直道过拟合”与“急弯欠拟合”之间的两难困境
--------------------------------------------------------------------------------
1. 遇到的现象与表象:
   - 若系统全程锁定使用 2 阶多项式 (二次抛物线 y = ax^2 + bx + c):
     在直道行驶时，明明车道线是笔直的，但拟合出的高次项系数 a 却随微小噪点频繁
     抖动，导致计算出的曲率 kappa 频繁跳变，小车直道巡航出现舵机高频微颤；
   - 若系统全程锁定使用 1 阶多项式 (直线 y = ax + b):
     在 90 度急转弯道上，直线根本无法贴合弯道弧线，曲率永远算出来为 0，下游
     控制器无法提前感知前方弯道并提前减速，导致高速入弯侧滑推头。

2. 物理与数学机理:
   - 直道或近场样本采样范围有限时，点集在几何上高度退化为一条狭窄线段，此时强制
     拟合二次项，多余的自由度必然会去拟合随机噪声，发生经典的“多项式过拟合”；
   - 急弯时车道线具有显著的曲率半径，一阶直线自由度不足，无法反映真实切线斜率变化。

3. 为什么这样改？(最终解决方案: 动态纵向物理跨度自适应升降阶)
   - 在底盘物理坐标系下实时计算点云的前向纵向物理跨度:
     dx_span = float(np.max(bx) - np.min(bx))
   - 决策分支:
     if dx_span >= 0.70:
         degree = 2  # 纵向跨度充分 (>=0.70m)，允许拟合二次曲线，解算曲率与前瞻切线
     else:
         degree = 1  # 纵向跨度较短 (<0.70m)，自适应降阶为稳健一阶直线，杜绝高次抖动
   - 并在二次拟合时通过 raw_kappa 动态调节前瞻距离 (lookahead_dist 0.70m~1.15m)，
     大曲率急弯缩短前瞻抑制切弯，直道拉长前瞻平稳巡航。


--------------------------------------------------------------------------------
【坑 6】传统滑动窗口在虚线大间隙与弯道急拐处的“丢线断线与跳变”
--------------------------------------------------------------------------------
1. 遇到的现象与表象:
   在小车经过地面虚线车道线时，由于虚线之间存在 20~40 厘米的空白间隔，传统的
   底部直方图扫描在空白处找不到峰值，返回 base_x = 0，滑动窗口直接缩回最左侧，
   导致当前帧彻底丢失，底盘控制器误触发刹车；
   在急弯拐角处，车道线快速向侧方偏折，上一层滑窗无法捕获足够的内点，滑窗序列
   直接断裂。

2. 物理机理剖析:
   传统滑窗算法假设车道线在图像底部是连续实线。但真实道路存在虚线、磨损脱漆、
   斑马线遮挡以及急转弯横向大偏移。单帧独立的直方图峰值极易受到空洞破坏。

3. 为什么这样改？(最终解决方案: 历史先验记忆 + 动态重定位 + 稀疏廊道保底 + 时序滤波)
   - 【历史先验记忆引导】:
     若当前帧底部直方图无有效像素，平滑沿用上一帧有效记忆横坐标:
     base_x = int(self.last_valid_x_px)
   - 【动态中心平滑重定位】:
     8 级垂直滑窗逐级爬升，当前窗口内点达到阈值 (min_recenter_pix=15) 时，
     以下一层内点均值作为新中心，平滑拐弯跟踪；
   - 【虚线稀疏特征廊道自适应保底】:
     若滑窗聚类总点数不足 40 点 (处于大虚线间隙)，自动激活全域动态廊道回退机制，
     提取整个车道廊道内的有效离散像素，保障拟合不中断；
   - 【时空一阶低通滤波与 6 帧防丢线守护】:
     对拟合参数采用 80% 当前帧 + 20% 历史帧的时空滤波平滑；允许连续 6 帧
     (约 0.2 秒) 视觉丢线容错，沿用历史轨迹平滑过渡，消除偶发斑马线闪烁。


--------------------------------------------------------------------------------
【坑 7】固定 ROI 在弯道深处的“截断视野”与动态视场呼吸机制
--------------------------------------------------------------------------------
1. 遇到的现象与表象:
   若使用固定梯形或矩形感兴趣区域 (ROI)，例如将右边界固定写死在 x=420px：
   在直道行驶时一切正常，但当小车向右或向左大角度转弯时，弯道深处的车道线
   在图像上会大幅度横向甩向右侧 (实测甚至延伸至 x=550~600px 区域)。固定 ROI
   直接把弯道远端车道线“一刀切”裁掉，造成前向拟合深度不足，曲率测不准。

2. 为什么不能简单将 ROI 设为全屏 (640px)？
   - 若不加任何横向限制直接开放全屏，小车在左转或靠边时，沙盘外围的多余模型、
     邻近车道的其他标线、建筑物外墙会进入检测范围，造成外侧虚假干扰。

3. 为什么这样改？(最终解决方案: 航向角轨迹引导的自适应动态 ROI)
   - 利用小车前向航向角 self.last_heading 动态预测车体未来行进趋势：
     if self.last_heading < -0.05:
         # 小车右转入弯: 弯内侧车道线向右偏移，动态将右侧视窗大范围向外延展 (上限 625px)
         extra_w = int(min(205.0, abs(self.last_heading) * 390.0))
         x_max = min(625, 420 + extra_w)
     elif self.last_heading > 0.05:
         # 小车左转: 车道线偏向内侧，收紧右侧视窗至 390px 排除沙盘外杂物
         x_max = 390
     else:
         x_max = 420  # 直道工况维持 420px 标准巡航视窗
   - 视场随航向角动态“呼吸伸缩”，直道紧凑抗噪，弯道开阔保全。

【坑 8】HUD 仪表盘中文渲染性能损耗、订阅门禁与终端环境污染
--------------------------------------------------------------------------------
1. 遇到的现象与表象:
   - OpenCV 的原生 cv2.putText() 仅支持英文字符集，传入中文直接崩溃或显示为乱码；
   - 使用 PIL 库渲染中文时，如果在每帧回调里都执行一次 ImageFont.truetype()，
     会导致严重的磁盘 I/O 和 CPU 飙升，FPS 从 200+ 暴跌至 40；
   - 节点每次启动发布大量长文本，导致终端排版混乱；且如果不管有没有人看都每帧
     生成高清 HUD 图像，白白浪费无人车宝贵的嵌入式算力。

2. 为什么这样改？(最终解决方案: 静态字体预加载 + 订阅者门禁 + 全中文 OSD)
   - 【静态字体一次性预加载】:
     在 __init__ 中静态单例加载系统开源中文字体 (/usr/share/fonts/opentype/noto/NotoSansCJK-Bold.ttc)，
     主循环中零磁盘 I/O 开销，纯内存绘制；
   - 【ROS 订阅者门禁机制 (Subscriber Gating)】:
     在 callback 中加入条件判断:
     if self.debug_pub.get_num_connections() > 0:
         # 仅在 RViz 或用户实际订阅 /lane_detect_debug 话题时才消耗算力渲染 HUD
         ...
     无人查看时跳过 HUD 渲染，算力开销降为 0，全力保证控制闭环；
   - 【极简终端启动与规范契约】:
     节点启动仅输出一句简洁的 rospy.loginfo("自适应检测启动成功")；
     所有运行状态（光照模式、逆Gamma、物理偏差e_y、航向角、曲率、RANSAC内点率）
     全部通过高质感半透明磨砂全中文 HUD 在影像上集成展示。

【坑 9】直道循迹左右“画龙”剧烈摇摆 (Hunting Oscillation) 的动力学根源与解耦消除
--------------------------------------------------------------------------------
1. 遇到的现象与表象:
   小车能够跟随车道线行驶并完成弯道拐弯，但在笔直的道路上无法平直稳定前行，
   而是以车道中心为轴，车头不断剧烈左右摆动、蛇形走位（工程俗称“画龙”）。

2. 物理与数学机理剖析 (三大根源):
   - 根源 A: 横向偏差 e_y 测量位置错误，引入了前瞻航向角 5 倍超调放大！
     * 在标准斯坦利 (Stanley) 控制理论中，横向误差 e_y 严格定义为【车辆前轴/底盘中心】
       到路径切线的垂直米制距离 (x=0 处)；
     * 原代码在阶段五计算 e_y 时，竟然错误地代入了前方 lookahead_dist (0.95m) 处的值：
       y_lane_metric = a*(0.95^2) + b*0.95 + c
       e_y = y_lane_metric - 0.45
     * 当小车直道巡航时，只要车头产生 1 度的极微小航向夹角 (e_psi ≈ 0.017 rad)，
       在 0.95m 远处就会产生 Δy = 0.95 * tan(1°) ≈ 1.7 厘米的假横向位移！
     * 斯坦利控制律公式: delta = e_psi + arctan(k * e_y / v_x)
       代入后展开: delta ≈ (1 + k * L_lookahead / v_x) * e_psi
       代入实测数值: 1 + (1.5 * 0.95 / 0.35) = 1 + 4.07 = 5.07 倍！
       仅仅 1 度的车头晃动，控制器竟然疯狂下发了超过 10 度的巨额反向打舵角！
       小车被强制猛甩到另一侧，导致正向超调变成反向超调，陷入永无休止的“自激振荡”。
   - 根源 B: 斯坦利控制增益 k_stanley 设定过大且缺乏阻尼项 (D 项):
     * 原代码设定 k_stanley = 1.50，在轻量级阿克曼小车 (轴距 0.20m) 且控制频率
       高达 30Hz 下，系统阻尼比严重低于 0.707 (属于典型欠阻尼系统)；
     * 系统缺乏对横向位移变化率 (d e_y / dt) 的微分阻尼抑制。
   - 根源 C: 底层 Gazebo 驱动角速度 omega 与转向角 delta 的物理量纲转换:
     * 底层仿真驱动接口接收的 cmd_vel.angular.z 是车体偏航角速度 omega (rad/s)；
     * 根据阿克曼运动学模型，物理转向角与角速度的关系为 omega = (v / L) * tan(delta)。
       直接把 delta 传给 angular.z 会导致物理转向角与控制预期失谐。

3. 为什么这样改？(最终解决方案: 坐标系解耦 + PD阻尼斯坦利 + 软死区)
   - 【物理中心严格解耦 (在 graduation_detect.py 中修复)】:
     计算车辆真实的横向物理偏差时，严格在小车刚体物理中心 (x=0) 处提取多项式截距：
     y_vehicle_base = float(fit_metric[-1])
     e_y = float(y_vehicle_base - self.target_lane_offset)
     将车辆横向位移 e_y 与前瞻航向角 e_psi 彻底物理正交解耦，切断 5 倍正反馈死循环！
   - 【PD 阻尼斯坦利控制律 (在 graduation_control.py 中重构)】:
     delta = e_psi + arctan(k_stanley * effective_ey / v_x) - k_d * (d ey / dt)
     * 将 k_stanley 调谐至临界阻尼最优区间 0.75；
     * 引入横向速度微分阻尼项 k_d = 0.15，当车辆向中线靠拢时主动施加阻尼反向舵角，
       实现零超调平滑贴线；
   - 【直道微小抖动软死区 (Deadband = 1.2cm)】:
     当横向偏差小于 1.2cm 时，判定为正常视觉像素离散波动，平滑衰减打舵，
     小车直道巡航如列车轨行般绝对平直，彻底消除“画龙”。
   - 【阿克曼物理量纲精准转换】:
     omega = (self.current_vx / self.wheelbase) * math.tan(self.current_steer)
     向 cmd_vel.angular.z 发布严密符合阿克曼底盘动力学的角速度。


================================================================================
【核心陷阱九】小车弯道“拒转直冲”、出弯死停与盲区寻线机制（借鉴 follow_lane_contest.py 核心精髓）
================================================================================
1. 遇到的现象与坑:
   小车在直道上巡航非常平直稳健，但在到达 90 度急弯拐角处时，小车完全不转弯
   （控制台打印转向角仅有 +0.6° ~ -7.5°），直愣愣地冲出弯道，随后车身脱离车道线，
   控制台立刻陷入死循环告警：
   [WARN] [丢线保护模式] 视觉车道线丢失或超时，车辆平滑减速刹停 (v=0.00 m/s)...
   小车彻底瘫死在弯道中，再也无法自恢复运行。

2. 为什么会这样？（深度剖析四大致命连锁死锁）:
   - 致命死锁 A: 动态 ROI 右边界 (x_max=420) 人工截断弯道，造成“感知死锁 (Deadlock)”
     * 在直道准备入右急弯时，前方车道线急剧向右弯折延展至图像 X=330~600 px 处；
     * 原代码在直道工况下设定 x_max=420，直接把画面中 90% 以上的弯道黄色像素（实测
       4823 个黄色点中有 4593 个点位于 X > 420）暴力裁剪成全黑！
     * 形成恶性死锁闭环：车头未转动 -> 历史航向角为 0 -> x_max 锁死在 420 -> 前方急弯
       被盲目裁剪 -> 算法感知不到道路右弯 -> 车体绝不打舵转弯！
   - 致命死锁 B: 多项式拟合阶数门槛过高导致弯道曲率退化为 0
     * 原代码设置必须满足 dx_span >= 0.70m 物理跨度才启用二次抛物线，否则退化为一阶直线；
     * 在急弯处由于相机仰角与几何透视压缩，小车视野内车道线纵向物理跨度实测仅为 0.46m；
     * 门槛过高导致算法在急弯处强行退化为一阶拟合，输出曲率 kappa 恒为 0.000/m！下游控制器
       认为前方一马平川，以 0.35 m/s 极速盲冲入弯，导致严重推头失控。
   - 致命死锁 C: 斯坦利控制律中 e_y 与 e_psi 在弯道处符号相反、相互抵消归零！
     * 实测终端数据: [横向偏差: +0.301 m | 航向角: -30.7° | 舵角: +0.6°]；
     * 当弯道向右拐时，切线航向角 e_psi = -30.7°（要求向右打舵 30°）；
     * 但原代码若在 x=0 处反向外推截距，算出的横向偏差竟高达 e_y = +0.301m（要求向左打舵 31.8°）；
     * 二者在斯坦利公式中代数相加: delta = -30.7° + 31.8° = +1.1°！本该满舵右转的弯道，
       转向角被完全抵消为 0°，小车如脱缰野马直冲沙盘外墙！
   - 致命死锁 D: 看门狗机制过于严苛，缺乏弯道盲区寻线过渡 (Corner Blind-Spot Traversing)
     * 阿克曼底盘在 90 度小半径弯道回转时，前置相机受限于视场角，车道线极易在 0.5~1.0 秒内
       滑出画面边缘或底部；
     * 原看门狗只要丢失超过 0.2 秒（6 帧），就立刻平滑减速刹停并将舵角归零；
     * 车辆一旦在弯心刹停，车头正好面朝外侧墙壁，黄色线永远不在视野内，陷入“永久死锁刹停”。

3. 为什么这样改？（汲取 follow_lane_contest.py 竞赛实战智慧）:
   - 【全景开放动态 ROI (Full-Field ROI)】:
     由于阶段一研发的 HSV+LAB 双空间并联特征提取对沙盘树木和墙壁具备 100% 绝对抗噪性
     （全幅画面中黄色误检像素为 0），因此将动态 ROI 彻底全景放开至 x_max = 625px！
     使相机在直道上即可一览无余地提前预判前方 600px 处的弯道大弧，切断感知死锁。
   - 【低门槛二次抛物线拟合 (dx_span >= 0.35m)】:
     将二次抛物线拟合门槛从 0.70m 调整为 0.35m，实测 0.46m 跨度的急弯能 100% 精准拟合
     出抛物线圆弧与真实道路曲率 (kappa ≈ 0.36/m)。
   - 【前瞻横向偏差与航向同向强化打舵】:
     在前瞻点计算横向位移 e_y，弯道处 e_y 与 e_psi 协同发力，共同输出满额极限机械舵角
     （-28° ~ -30°），确保车辆以最大转向能力敏捷切入弯道内侧。
   - 【弯道盲区辅助寻线看门狗 (Corner Blind-Spot Assist)】:
     借鉴 follow_lane_contest.py 中 "x < 0 时以 0.19 m/s 保持 ang_vel = -1.2 强力过弯" 的核心精髓：
     * 控制器监控丢线瞬间小车的打舵历史状态：若车辆原本正处于打舵转弯中（转角 > 5°），
       说明正处于急弯视锥盲区！
     * 触发 1.2 秒高优先级【弯道盲转辅助模式】：小车绝不刹车，维持 0.18 m/s 低速并锁定
       26° 极限打舵角，依靠车身回转动力学平稳扫弯；
     * 当车身自旋 90 度后，黄色车道线瞬间重新落入相机正前方视场，看门狗无缝平滑切回斯坦利闭环；
     * 仅当直道丢线或盲转超过 1.2 秒仍未找到线时，才执行主动降速安全刹停。
   - 【曲率与舵角双重自适应降速 (Speed Planning)】:
     直道巡航稳定在 0.25 m/s；入弯检测到曲率 kappa > 0.2 或舵角 > 8° 时，自动平滑减速至
     0.16 ~ 0.18 m/s（完全匹配 contest 经典 0.19 m/s 稳健过弯速率），消除离心侧滑与推头。
